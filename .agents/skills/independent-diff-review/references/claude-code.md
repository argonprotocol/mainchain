# Claude Code reviewer

Use Claude Code as the independent discovery reviewer when selected and authorized. Honor the user's provider choice; availability or a different provider name alone does not establish superiority. It replaces the usual Codex discovery subagent; the coordinator still validates every finding. Do not automatically run both providers on every small change. A second review needs a concrete coverage gap or unresolved concern.

## Start a fresh, bounded review

1. Locate the installed executable and read its local `--version` and `--help`. Verify authentication using its status command without printing account details or credentials. Preserve the configured model unless the user selected another.
2. Give it the same neutral packet from the main skill: frozen base/head or immutable snapshot, intended outcome, explicit constraints, source restrictions, and this procedure. For independent discovery, keep prior findings, author reasoning, memory, benchmark answers, and later fixes out of its context. For feedback validation, include the supplied comments and their original/requested current revisions as candidates to check; keep unrelated context and benchmark answers out. Request its own producer/consumer traces and disproof attempts.
3. Use a fresh noninteractive session with read-only tools. With a CLI that supports them, use `--print`, `--safe-mode`, `--no-session-persistence`, `--permission-mode plan`, and `--permission-prompts none`. Disable browser integration and unrelated MCP servers; explicitly allow only needed file reads and source-inspection commands. Limit file reads to the procedure, explicitly scoped working files or snapshots, and necessary pinned dependency source. Prefer Git object reads for committed source; do not grant the review packet access to unrelated local files. Verify the reviewer can read the procedure and exact Git objects through `git show`, `git diff`, and `git grep`, or provide an immutable snapshot when Git access is unavailable. A denied read is a coverage gap, not a successful review. Verify flags against the installed help rather than assuming every version supports them. Never bypass permission checks. Plan mode alone is not evidence that an arbitrary shell command is read-only.
4. Source review may send repository contents to the selected provider. Send only material necessary for the review, excluding credentials, session data, and real user or production-account information, including in untracked files such as `.env`. These exclusions apply to provider input as well as reports. Read standing authorization in the applicable `AGENTS.md` and honor explicit session authorization. Do not ask again for a review already covered by that authorization. Honor any enforced approval boundary. If approval review blocks that transfer, explain its stated reason and request the specific missing authorization. Do not work around the rejection. Continue independent work that does not depend on the transfer.
5. Capture the result in temporary space. Request structured findings, rejected candidates, coverage, and limitations. Record actual model/provider metadata, reviewed revision, completion status, elapsed time, and usage/cost fields only when returned. A launched process, an authentication success, or an empty interrupted response is not a completed review. Preserve partial coverage explicitly after timeout or tool denial.
6. Apply the main skill's coordinator disproof pass. If sending counterevidence back, label that run as validation; do not present it as a second blind discovery review. Use a narrow independent follow-up only where the original reviewer could not inspect a required boundary.

Keep credentials, account/session details, raw diagnostics, and production data out of tracked reports. For ordinary reviews, summarize decisive findings and exceptions rather than committing provider transcripts. Review-only authorization does not authorize external comments, code changes, staging, commits, or pushes.

## Benchmarking providers

Freeze the same packet, scope, instructions, and effort cap before comparison. Record the actual provider/model and any unavailable tools. Score root causes after reports are fixed. Keep a provider comparison separate from an instruction comparison; changing both at once does not establish which change helped. A provider's additional valid findings do not erase known misses. Use observed results, not model names, as evidence of capability.
